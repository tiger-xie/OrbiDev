# ADR-016：RADP/1 编解码与业务验证边界

日期：2026-10-17。范围：TASK-M3-01，不包括 WebSocket 服务端或配对认证。

## 决策

RADProtocol 只依赖 QtCore，协议 DTO 与 SessionManager 的业务模型分开。采用同步、无状态、无 IO 的编解码函数；调用者持有输入与返回值，不隐式保存连接、认证或会话状态。

JSON 控制消息使用版本化 envelope。二进制终端消息固定为 `RADP(4) | version(1) | kind(1) | session_uuid(16) | sequence(8) | length(4) | bytes(N)`；多字节整数采用大端序，UUID 使用 RFC 4122 的 16 字节顺序。整个消息上限 65536 字节，因此二进制有效载荷上限 65502 字节。

接收和发送均验证数据。解码入口先检查总长度，再解析内容；拒绝未知版本、无效类型、非法 UUID、头部截断、声明长度不符和尾随字节。终端字节保持原样，不转换 UTF-8，也不解释 ANSI。

UUID 语法正确不代表会话存在或调用者有权限。会话存在性检查与编解码明确分开，使用调用方提供的已知会话信息；M3-02 必须先鉴权，再执行会话授权和 SessionManager 操作。不得将本阶段测试通过视为已完成网络安全验证。

对外错误使用明确的协议错误码与安全消息，不把输入包、解析器错误片段或系统错误详情原样拼入响应。版本协商只决定双方是否支持 RADP/1，不授予任何访问权限。

## 取舍与后续约束

- 不复用业务 SessionId 或 Error 作为协议 DTO，避免协议库依赖会话实现；后续路由层承担显式转换。
- 不实现通用 RPC 框架、流式拼包器或网络监听；WebSocket 完整消息由 M3-02 交付编解码函数，接收缓冲同样必须设限。
- 编解码不负责检查二进制序号是否单调，序号校验、输出截断通知和重连状态由连接与会话层持有。
- 具体支持的类型、字段规则、测试入口与证据见 [M3-01 说明](../M3-01_协议编解码.md)。
